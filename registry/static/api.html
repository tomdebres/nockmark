~nockmark / api

Everything the board shows comes from these endpoints. No accounts, no keys: a valid STARK proof of the server's own challenge is the only credential a submission needs.

Read
GET/leaderboard

The ZK board (?track=zk says so explicitly). Ranked rows first: ZK v5 runs, by verified Tip5 hashes per second. Then every run from before Anthropos, in their own unit, unranked.

  • rank — 1-based among current-rules rows; null on every unranked row
  • rules — server-attested era: anthropos (ZK proof %5, ranked) or pre-anthropos (complete %3 proofs/sec, unranked)
  • proving (v5 rows) — pipelined or serial, as the client reported it: a label, never a ranking input; see below

Pipelined and serial rows. The tier gives each win about twice a proof's worth of grinding. A pipelined client proves each winner while it keeps grinding, so the window is the grind plus one proof and the ranked rate is about 97 % of the true one at k = 16. A serial client grinds all k wins first and proves them after, which caps it at about two thirds. Both are honest lower bounds, but they do not rank fairly together. Every run this server committed before 2026-11-13 00:00 UTC came from the serial client, the only one there was; once a board has a current-rules row committed after that, those older rows follow the ranked ones with rank: null. That cut uses the server's own clock. The proving label is the client's word, so it moves no rank: a run made later with --serial is ranked with the rest, at the rate its idle grinder cost it.

A v5 row (rules: anthropos):

  • verified_zk_hashes_per_sec_lb — k · expected_attempts_per_win / server-observed window (mint → submit, proving included); the ranked lower bound
  • grind_zk_hashes_per_sec — the same numerator over the client's grind time; informational only
  • expected_attempts_per_win — the tier: p5 / (target + 1) Tip5 hashes, with p the Goldilocks prime
  • sigma_frac — ±1σ as a fraction of the rate (1/√k)
  • target, attempts, win_nonces — the target the wins were verified against (5 base-p limbs, least significant first, as decimal strings), its tier, and the winning nonces
  • est_nock_per_day, est_usd_per_day — from the ranked rate, at the difficulty and price on /economics

A pre-Anthropos row (rules: pre-anthropos) keeps its old shape: proofs_per_sec (k / server window) and self_reported_pps. Those rows measure complete proofs per second, the mining unit before height 147,500. They carry no earnings estimate: network difficulty counts Tip5 hashes now, so a proofs/sec figure prices nothing.

curl 'https://nockmark.xyz/leaderboard?track=zk'

?track=ai returns the AI-PoW board instead: rates in MAC-equivalents per second, plus est_nock_per_day and est_usd_per_day computed from the ranked verified_mac_per_sec_lb. Those two are absent until an ai-pow block has actually been seen at the chain tip — AI difficulty cannot be derived from the ZK figure. Only rows verified under the current AI rules (hardened) are ranked.

GET/runs/:id

One verified run by id, same shape as a leaderboard entry, with its board rank. Each track numbers its runs separately, so the track picks which: ?track=zk for a v5 run, ?track=ai for an AI run, and no track for a pre-Anthropos run (the links older clients printed).

curl 'https://nockmark.xyz/runs/1?track=zk'
GET/economics

Every input behind every estimate this registry publishes, so you can recompute any of them yourself: both difficulties — ZK (difficulty, expected attempts per ZK block — Tip5 hashes since height 147,500) and AI (ai_difficulty_mac_equiv_per_block = 2^256 / (ai_target + 1), expected MAC-equivalents per block) — each with its own *_observed_at and *_age_secs; the NOCK price with its source and age; the block reward; both block times; and the MAC↔ZK-attempt exchange rate (14,285,714 MAC-equivalents per Tip5 hash since height 154,500). difficulty_source and ai_difficulty_source name where each figure came from — nockscan first, NockBlocks when it fails — and block_reward_observed_at says the reward (the 80% miner share) was read from the chain rather than configured. model carries the formulas, notes.excludes what they do not account for, and notes.zk_board which ZK rows are priced and why the pre-Anthropos ones are not.

Anything unobserved is omitted rather than defaulted: no AI block seen means no ai_* keys, no price means no USD anywhere. Pass ?zk_hashes_per_sec= or ?mac_per_sec= to price a machine of your own on either puzzle. The old ?pps= is answered with a pps_note saying why, not with a number.

curl 'https://nockmark.xyz/economics?zk_hashes_per_sec=1.8e7&mac_per_sec=3.3e14'
GET/economics/history

ZK difficulty over time as [unix_secs, difficulty] pairs (points before height 147,500 count proofs, after it Tip5 hashes), oldest first, thinned to ≤ 1000 points. ?hours= bounds the lookback (default 168, max 2160).

curl 'https://nockmark.xyz/economics/history?hours=720'

POST/challenge?track=zk

Mint a ZK v5 challenge. The ranked rate is measured from this moment to submission, server-side. Returns:

  • nonce — the kernel-minted u64 the rest derives from (decimal string)
  • challenge — C = blake3("nockmark-zk-v5" ‖ nonce_le8), hex
  • commitment — the block commitment to grind: C as a little-endian 256-bit integer written in base p (5 belts, least significant first). Rule commitment_rule.
  • target, attempts — the benchmark target Tb (5 base-p limbs) and the tier it realises
  • k — winners required; pow_len 64; proof_version 5; nonce_rule

Belts travel as decimal strings: they run to 264, past what a JSON number survives in JavaScript.

?attempts= picks the tier: expected Tip5 hashes per win, rounded to the nearest power of two and clamped to [212, 231] (default 220). The target is Tb = ⌊(p5 − 1) / attempts⌋ − 1, so that p5 / (Tb + 1) gives the tier back exactly. As on the AI track, a tier cannot inflate a rate: an easy one earns less credit against the same proving time, and a hard one has to be ground out. tock zk-bench sizes it at twice the machine's own proving time and proves each winner while it keeps grinding, which makes the ranked rate about 97 % of the true one at k = 16 on every host (two thirds for a serial run).

Without ?track=, POST /challenge and POST /run answer 410 Gone: they were the complete %3 proofs/sec submission, retired with Anthropos.

curl -X POST 'https://nockmark.xyz/challenge?track=zk&attempts=16777216'
POST/run?track=zk

Submit k winners, one %5 proof each, in strictly ascending nonce order (base-p, most significant limb first).

  • nonce, proofs[k] — the challenge and the winners' base64 proof jams
  • hardware, prover_version — self-described labels (rates are not self-described)
  • grind_elapsed_ms — client-measured grind time; displayed, never ranked
  • proving — optional label, "pipelined" or "serial" (the default); any other value is refused

Nothing digest-shaped is taken from the client. Per proof, cheapest first:

  • version is %5: a %3 proof is refused, as mainnet has refused them since height 147,500
  • object 0 is a %puzzle whose commitment is this challenge's and whose len is 64
  • its Tip5 digest is re-derived from the submitted object 0 the way consensus does (+proof-to-pow), must equal upstream's own v5_pow_digest of the object's commitment, nonce and length, and must be ≤ Tb (consensus's +check-target)
  • every polynomial object is in canonical form (+canonical-pow-proof)
  • across the submission, one win per nonce. Consensus treats everything after object 0 as a witness envelope: two different proofs of one nonce are one win, so the dedupe is on the nonce, not on the proof bytes
  • the STARK verifies with upstream's native verifier, and again with the consensus Hoon verifier
tock zk-bench --kernel assets/miner.jam \
  --submit https://nockmark.xyz
AI-PoW track (CPU and GPU)

What these rates cover. The AI track grinds the canonical block shape, and the GPU rows are behind upstream: they were measured at pin c8d6b13e, under the legacy proof rules, with the generic CUDA kernel that still serves this shape. Two days after that pin upstream made a peak kernel on its own dense shape the production GPU path — the same card goes from 0.19 to 335 TMAC/s, about 1,700x. Read the GPU rows as a floor for the hardware. That shape is now the dense-peak statement below (CPU rows first, from rented hosts); GPU re-runs are pending. Nockchain also admits mining inside real model inference, at throughput comparable to the optimised dedicated kernel — the notable part being that the compute is dual-use, not that it is faster.

POST/challenge?track=ai

Mint an AI-PoW challenge for the Logos puzzle (INT8 tiled matmul + recursive STARK certificate). Returns the kernel-minted nonce, the 32-byte challenge derived from it (blake3("nockmark-ai-v1" ‖ nonce_le8)), the jackpot target Tb, k (wins required), the fixed params, the statement, and the grind rule.

?statement= selects which AI-PoW statement to be challenged on. It defaults to dense, so a request without it means exactly what it always did.

  • dense — the single-tile statement (m=8, k=1024, n=8, noise_rank=64, tile=8), matrices seeded from the challenge. Grind rule extranonce-le8-v1: attempts are extranonces 0, 1, 2, … encoded as 8 little-endian bytes, and a win is jackpot ≤ target, unscaled.
  • canonical-moe — the canonical MoE (GROUPED_GEMM) block the production gateway-free miner submits, and the one the upcoming CUDA backend accelerates: m=64, k=1024, n=64, noise_rank=64, tile=8, with hw=8, e=2, top_k=1. The challenge binds through the Pearl header's aux commitment. Grind rule canonical-ordinal-v3: attempts are u32 ordinals 0, 1, 2, … that offset the header timestamp — not an 8-byte nonce. A win is jackpot ≤ target × F with F = 216, so the same 32-byte target means F times less grinding here than on the dense statement. The response says so explicitly: params.shape_work_factor and params.target_is_scaled_by_shape_work_factor.
  • dense-peak — mainnet's production AI shape, the one upstream's peak CUDA kernel grinds (#159): m=4096, k=8192, n=32768, noise_rank=512, 16×16 tiles, production synthetic matrices. One extranonce fixes a Pearl transcript; each of its 219 output tiles is one attempt, worth F = 16·16·8192 = 221 MAC-equivalents. Grind rule peak-extranonce-tile-v1: an attempt index is extranonce · 2^19 + tile (tile = row_tile · 2048 + col_tile, upstream's order), and a win is jackpot ≤ target × 2^21. The challenge binds through the Pearl header's aux commitment, as on canonical-moe. Tiers run to 236, the response carries window_ms, and the challenge lives 3 h: one certificate takes 60–76 s and 12–15 GB on an M1 Max, so 16 wins at twice the proving time, proved after the grind, do not fit an hour (pipelined, they need about 33 certificates' worth). A dense-peak challenge takes only dense-peak wins, and the other way round. Its GPU path (--gpu) is upstream's peak kernel, which runs only on compute capability 12.0 (RTX 5090 class).

?attempts= requests a difficulty tier: the expected grind attempts per win you want to be targeted at. The server derives the target from it — respecting each statement's own semantics, so the same tier is a different 32 bytes on dense and on canonical-moe — and echoes the granted value back as attempts. Clients still read target; omitting the parameter reproduces the previous behaviour exactly, target and response alike.

  • Rounded to the nearest power of two internally, so the target is a single set bit and tier → target → score round-trips exactly and reproducibly.
  • Clamped to [212, 230] (dense-peak: [212, 236]); compare the echoed attempts against what you asked for to see the clamp. The ceiling is the challenge expiry: at ~3 M attempts/s, 230 is ~6 min of grinding per win, and a challenge goes stale 1 h after it is minted.

Why letting the client choose cannot inflate a rate. The ranked figure divides real MAC-equivalents by a window this server observed, and a tier only changes how much of that window is grinding rather than certificate proving the grind cannot hide: an easy tier earns less credit against the same proving and therefore scores lower, so there is nothing to gain by asking for one. A hard tier cannot lift a machine above its true throughput either, because every attempt it is credited for is genuinely performed — the credit is exactly the expected attempts at the target the wins were verified against, and a win only exists if a jackpot really cleared it.

curl -X POST 'https://nockmark.xyz/challenge?track=ai&statement=canonical-moe&attempts=1048576'
POST/run?track=ai

Submit k jackpot wins. Each win's certificate is verified end-to-end before anything is recorded: statement re-derived from (challenge, extranonce) — matrices re-synthesized, every public input re-checked, HASH_JACKPOT ≤ target — then the compact STARK verify against the server's own setup.

  • nonce — the challenge's nonce (decimal string)
  • statement — dense (default when absent), canonical-moe or dense-peak; picks the verify rules, the target and the blob format
  • wins[k] — {extranonce, cert_b64}, strictly ascending (ground 0, 1, 2, …). For canonical-moe the field carries the u32 ordinal; for dense-peak, the attempt index.
  • hardware, prover_version — self-described labels (rates are not self-described)
  • grind_elapsed_ms — client-measured, grind start to the last win found; displayed, never ranked
  • proving — optional, "pipelined" or "serial" (the default), as on the ZK track

For canonical-moe the submission carries nothing but the certificate and its public inputs: the whole statement — Pearl header, mining config, matrix commitments, routing, opened indices, jackpot — is re-derived here from (challenge, ordinal) and the jackpot is gated at target × F before the compact STARK verify.

For dense-peak each cert_b64 is the jammed %ai-pow block artifact a node receives (~147 KB, cap 160 KB). Per win, the server decodes it with the consensus jet's own bounded decoder; checks that it is dense (no MoE tail), carries dense-peak's mining config and m×n, opens the tile the attempt index names, and carries this challenge's Pearl header at that extranonce; then runs upstream's consensus verifier (verify_ai_pow_block_artifact_with_verification_rules, the function behind %ai-pow-verify-v2) under ConsensusBatch: admission limits, canonical FRI witnesses, the 219 trace cap, the challenge bound as the block commitment, jackpot ≤ target × 2^21, and the compact recursive STARK, against a verifier setup this server derives from the shape and a key digest it pins. As in consensus, the matrices are the miner's choice; a tile over other matrices costs the same 221 MACs.

GET/leaderboard?track=ai

All three statements rank on this one board, by verified_mac_per_sec_lb. They share it because MAC-equivalents is precisely the unit consensus uses to compare AI work of different shapes: expected MAC-equivalents per block is 2^256 / T whatever tile shape the miner picked, which is what makes the AI puzzle's fork-choice weight meaningful in the first place. An attempt is F = 216 MAC-equivalents (an 8×8 tile over k=1024) on dense and canonical-moe, and 221 (a 16×16 tile over k=8192) on dense-peak; the attempt count follows each statement's target semantics — 2^256/(T+1) for dense, 2^256/(T·F+1) for canonical-moe and dense-peak. Every row carries its own statement and its own target, so a re-calibration cannot rewrite how an older row was scored.

  • statement — dense, canonical-moe or dense-peak
  • expected_attempts_per_win — the difficulty tier this run was measured at, derived from its own stored target (so rows from before tiers existed carry it too). A tighter lower bound comes with a harder tier, because more of the window was grinding and less of it proving.
  • verified_mac_per_sec_lb — k · attempts-per-win · F / server window (issue → submit, proving included); the ranked lower bound
  • grind_mac_per_sec — same numerator over the client grind window; informational only
  • zk_attempt_equiv_per_sec — MAC/s ÷ 14,285,714, the consensus MAC↔ZK-attempt exchange rate since height 154,500; a ZK attempt is one Tip5 hash since Anthropos (rows served before M7 divided by the Logos rate, 25.75e9 per complete proof)
  • sigma_frac — ±1σ as a fraction of the rate (k wins is Poisson: 1/√k)
  • rules — the proof rules the wins were verified under, recorded by this server at acceptance: hardened or legacy
  • proving — pipelined or serial, client-reported; a label only
  • rank — 1-based among hardened rows; null on legacy rows, and on rows committed before 2026-11-13 00:00 UTC once a newer hardened row exists (the ZK board's rule, above)

Mainnet has admitted only Hardened AI certificates since height 154,500, and since 170,000 a canonical-MoE block must also route every token exactly top_k times. This registry pins nockchain ed1edfcc and verifies new wins under exactly those rules: a legacy certificate is rejected. Rows accepted before that pin carry rules: legacy and stay on the board, listed after the ranked rows with rank: null. Older still, rows proved before pin c8d6b13e used the pre-Pearl-V3 statement, whose AIR was later hardened upstream (urange8 lookup fix). Cross-era rate comparisons are fair — the grind is the same work — but each row's certificates were verified under its own era's rules. prover_version is the client's own label; rules is the server's.

curl 'https://nockmark.xyz/leaderboard?track=ai'
429rate limits

The two POST routes are rate-limited per IP. Over-limit responses carry a Retry-After header and {"retry_after_secs": …} in the body — sleep that long and retry.
